# Голосование — 1.0.1

## Правила и расчёт

`/like <игрок> <причина> [комментарий]` и `/dislike` принимают обязательное локализованное название причины
из `/rep reasons` или прежний стабильный ID. Разрешены известные серверу офлайн-игроки; поиск имени использует только
онлайн-игроков и кэш Paper. Некэшированное имя не вызывает запрос к Mojang. За себя голосовать
нельзя. Истории: `/rep history [страница]` (полученные) и `/rep given [страница]` (отправленные).

По умолчанию требуются 30 часов суммарного игрового времени и 7 суток с **первого входа на
этот сервер**, а не создания Mojang-аккаунта: Paper не предоставляет достоверную дату его
создания. Источник — `Statistic.PLAY_ONE_MINUTE / 20` и `Player.getFirstPlayed()`. Все права
и факты проверяются серверным адаптером на потоке Paper, включая обращения через API.
Для новой операции голосующий должен быть онлайн; цель может быть офлайн.

Во внешних интерфейсах можно показывать `%statistic_time_played%` при установленном
соответствующем PlaceholderAPI expansion. Eligibility использует числовое значение Paper
напрямую, поэтому не зависит от наличия expansion и формата его отображения. Встроенный
GUI не выполняет произвольные PlaceholderAPI-шаблоны из переводов.

В scope действует одна активная оценка от автора цели. Исторический расчёт версии 1:

```text
contribution = sign(type) × effectiveWeight
communityAfter = communityBefore − oldActiveContribution + newContribution
visibleAfter = communityAfter + systemScore
```

Default веса положительного/отрицательного голоса равны 1. Администратор может изменить
base weights; старые события сохраняют свои base/effective weights и версию расчёта.
Замена вычитает **сохранённый** старый вклад и прибавляет новый, отзыв убирает старый вклад.
Системная оценка и tier не меняются, revision цели увеличивается на 1. Legacy community
сохраняется как исходная база. Переполнение long отклоняет операцию целиком.
**С Phase 3 default новые голоса используют дробную версию 2** из anti-abuse.yml;
политика весов/pending и точность подробно описаны в [ANTI_ABUSE.md](ANTI_ABUSE.md).
Trust скрыт, ранги/титулы не добавлены.

`repeat-policy: REPLACE` разрешает замену; повтор идентичного активного type/reason/comment
с новым ID отклоняется. `ONCE` запрещает новое голосование той же пары даже после отзыва.
`allow-revoke` управляет `/rep revoke <игрок> [комментарий]`. После отзыва с REPLACE можно
подать новый голос; суммарный вклад пары всё равно ограничен одним активным голосом.

**Каждая** новая успешная операция — добавление, замена, отзыв — расходует дневной лимит и
запускает общую паузу и паузу пары. Ошибки и повтор того же operation ID ничего не расходуют.
Общая пауза по умолчанию 7200 секунд между операциями автора по любым целям в одном scope.
Пауза пары тоже 7200 секунд. Квота определяется текущей visible reputation автора:

| Репутация от | Лимит операций в день |
|---|---|
| ниже 25 | 3 |
| 25 | 4 |
| 100 | 5 |
| 250 | 6 |
| 500 | 8 |
| 1000 | 10 |

Граница дня — календарная дата `reset-zone` и час `reset-hour`, default UTC/00:00; переходы
DST учитываются. Повышение/понижение репутации меняет доступный лимит при следующем запросе.
Счётчики и cooldown восстанавливаются из журнала, а не сбрасываются при рестарте.

Положительные/отрицательные статистики считают **активные** голоса. Unique voters — число
разных авторов за всё время, включая отозванные голоса. История хранит все события, тип,
причину, комментарий, автора, цель, время, веса, ссылку на предыдущее событие и изменение
community. Сортировка — sequence по убыванию, статус active вычисляется на момент чтения.

## Конфигурация и сообщения

Полный рабочий пример — `reputation-paper/src/main/resources/voting.yml`; version 1.
Файл появляется только если отсутствует. Изменения применяются при рестарте.

| Параметр | Default / допустимые значения |
|---|---|
| minimum-playtime-seconds | 108000, 0..2147483647 |
| minimum-account-age-seconds | 604800, 0..2147483647 |
| cooldown-seconds / pair-cooldown-seconds | 7200, 0..2147483647 |
| base-daily-limit | 3, 1..10000 |
| daily-thresholds | упорядоченные `{score, limit}`; score ±1000000000, limit 1..10000 |
| reset-zone / reset-hour | UTC / 0; ZoneId и час 0..23 |
| repeat-policy / allow-revoke | REPLACE или ONCE / true или false |
| maximum-comment-length | 250, 1..2000 Unicode code points |
| positive-weight / negative-weight | 1, 1..1000000 |
| history-page-size | 9, 1..36 и не больше числа GUI content-slots |
| notify-target | true; уведомление онлайн-цели после нового durable commit |
| open-gui-on-profile | false; true открывает GUI при `/rep [игрок]` у игрока |
| permissions | семь настраиваемых узлов; см. PERMISSIONS.md |
| reasons | 1..128 причин; id `[a-z0-9_-]{1,32}`, message — ключ перевода, types — POSITIVE/NEGATIVE |

Пример пользовательской причины:

```yaml
reasons:
  teamwork:
    message: reason-teamwork
    types: [POSITIVE]
```

Добавьте `reason-teamwork` в RU/EN lang-файлы. Сообщение причины не должно иметь placeholders.
Убрание причины не удаляет историю: старый неизвестный ID отображается как ID. Комментарии
обрезаются по краям, внутренние управляющие символы и непарные суррогаты запрещены.
Коды причин приводятся к нижнему регистру. Динамические комментарии/имена вставляются plain
Components; MiniMessage из пользовательского ввода не выполняется.

Все `vote-*`, `gui-*`, `reason-*` сообщения поставляются на RU/EN. Старые lang-файлы получают
недостающие shipped keys в памяти, custom значения не перезаписываются. Свой язык `/rep language`
сохранён. Для настройки новых сообщений скопируйте нужные ключи из bundled примеров в старые файлы.
Неправильные enum, границы, порядок thresholds, права, reason keys и переводы блокируют запуск.

## GUI

`/rep gui [игрок]` открывает GUI. В профиле видны репутация, active +/−, исторические unique
voters и доступные действия: положительный/отрицательный голос, отзыв, полученные/свои
отправленные голоса. Выбор причины отправляет голос без комментария; комментарии доступны
в командах/API. История и список причин имеют страницы, навигацию и кнопку закрытия.

`gui.yml` version 1 определяет размер 45/54, content-slots (уникальные индексы 0..35), слоты
кнопок в остальных рядах и материалы. Пересечение кнопок одного экрана/невалидный material
отклоняется. Названия, заголовки и lore — в lang-файлах (`gui-*`). Права проверяются снова
при отправке; собственный профиль не предлагает голосование за себя.

GUI принадлежит конкретному UUID и экземпляру сессии. Любые переносы, shift/number/double
click, offhand, drop, drag и клики нижнего инвентаря отменяются. Действуют только сопоставленные
левые клики верхнего окна. Повторный клик во время запроса игнорируется; переключение окна
отложено на следующий tick. Callback обновляет лишь всё ещё открытый тот же экземпляр,
не открывает закрытое окно и не отправляет новую операцию после ухода игрока.
При отключении плагина все его окна закрываются до удаления слушателей; чужие окна не затрагиваются.
Это не предотвращает автоматизированное голосование вне GUI; правила применяются общим сервисом.

## Хранение, сбои и эксплуатационные границы

Исторический JSON v2 хранит profiles/preferences/**votes в одном checksummed snapshot**. Один atomic rename
фиксирует журнал и репутацию вместе; отдельные несогласованные vote/profile файлы не используются.
При чтении проверяются уникальность ID/sequence, цепочки пары, hash запроса, расчёты и итоговые
профили. Читается формат v1 Phase 1.1; запись выбирает формат 2–7 по сохранённым разделам с сохранением старой копии.
JSON имеет полную сериализацию/валидацию O(N) и fsync на запись, ограничение 64 MiB и полное
состояние в памяти. Рост истории требует перехода к SQL. `.bak` — предыдущий snapshot, не архив
всех поколений; восстановление старого backup может потерять последние операции.

Журнал введён SQLite/MySQL V2; текущая SQL schema до 7. WAL/FULL/busy timeout и один управляемый writer SQLite сохранены; MySQL сохраняет additive checksummed migrations, InnoDB transactions, prepared statements, Hikari pool и ownership.
`dr_votes.operation_id` и sequence уникальны; `dr_active_votes` имеет PK(scope,voter,target).
Операция атомарно проверяет правила/квоту, пишет event, меняет active index и профиль. SQL
проверяет согласованность полного журнала и индекса при старте/backup. Обычные запросы используют
индексы и постраничную выдачу. Полная startup/migration проверка требует O(N) времени/памяти.
Один владелец физического backend; несколько независимых shared writers не поддерживаются.

При сбое до/после SQL commit или JSON rename результат может быть неопределённым для caller.
Успех отправляется лишь после завершения durable записи. API-потребитель повторяет **тот же
operationId и те же поля**; новый ID обозначает новую операцию. Команды/GUI генерируют ID сами;
после неопределённой ошибки проверьте `/rep given` перед новой командой. Backend не заменяется
другим; JSON с неопределённой записью fail-closed до проверки/рестарта. Событие API/уведомление
не является durable очередью доставки: авария после commit до callback может потерять уведомление,
но не голос. Повторный запрос не рассылает уведомления повторно. Порядок callbacks между
workers не гарантируется, сортируйте по sequence. Ошибки listeners не меняют committed результат.

Backups, explicit recovery, quarantine и offline migration — [STORAGE.md](STORAGE.md).
Все шесть направлений переноса включают **весь журнал**, request IDs, веса, цепочки, квоты и
cooldown, active index строится заново и сверяется. Source/target/backup сравниваются полностью
до активации config, pending target не запускается. Старые данные не удаляются. Сохраните внешний
backup перед обновлением. Downgrade не поддерживается: JSON v2/SQL V2 блокируют старый формат;
возврат требует восстановления согласованного полного backup Phase 1.1, с потерей новых голосов.
SQL миграции V1 не менялись. Не редактируйте журнал/профили вручную.

Локальные тесты не доказывают работу при реальной потере питания, production TLS, многосерверной
нагрузке или подлинности аккаунтов offline-mode. Отдельный runtime QA-клиент работает только на
loopback offline сервере, не является production-клиентом и не входит в plugin JAR.

## Изменения Phase 3

Private protection state введён в format/schema 3; текущая версия поддерживает JSON до 7 / SQL schema 7. Active определяется
сохранённым pair pointer; latest pending может отличаться от active. Статистика учитывает
применённые active, а история сохраняет все попытки с durable commit. Public outcome
показывает PENDING/ACCEPTED/REVOKED/SUPERSEDED/INVALIDATED без Trust/сигналов.
В чате RU/EN сообщается pending или факт расчёта вклада, GUI после отправки использует
тот же pipeline и подтверждение. В истории Item.active=false не означает автоматически
нарушение: запись может быть pending, отозвана или заменена; точный публичный статус — outcome.
Новые правила применяются только к будущим оценкам. V1/V2 SQL migrations не менялись.
Перед обновлением сохраните полный backup, включая trust.yml/anti-abuse.yml и lang.

## История по причинам

`/rep gui <игрок>` открывает профиль с переходом в причины и историю. При `open-gui-on-profile: true` доступен также `/rep <игрок>`; текстовый режим сохраняет подсказку перехода. Категории: все, положительные, отрицательные, отдельный canonical reason ID; режимы полного журнала и действующих оценок. Счётчики учитывают текущий active index, включая замену, отзыв и модерацию. Отключённые причины остаются доступны. RU/EN меняют подписи, не запросы и не записи. [Подробности и размеры](ADMIN_UX.md#причины-и-история-игрока).

## Локализация и настройка причин

Для `ru_RU` автодополнение, ответы автору, уведомления цели, история и меню используют русские названия; для `en_US` — английские. Язык выбирается существующей `/rep language`. API, Trust и журнал продолжают использовать ID. Старые записи не мигрируют.

| ID | RU | EN | Тип |
|---|---|---|---|
| helpful | Помощь игрокам | Helping players | + |
| friendly | Дружелюбие | Friendliness | + |
| fair | Честная игра | Fair play | + |
| trustworthy | Надёжность | Trustworthiness | + |
| active | Полезная активность | Useful activity | + |
| community | Вклад в сообщество | Community contribution | + |
| builder | Хорошее строительство | Great building | + |
| trader | Честные сделки | Fair trading | + |
| teamwork | Командная работа | Teamwork | + |
| mentor | Помощь новичкам | Mentoring newcomers | + |
| rude | Грубость | Rudeness | − |
| unfair | Нечестное поведение | Unfair behavior | − |
| toxic | Токсичность | Toxicity | − |
| scam | Обман | Scamming | − |
| griefing | Гриферство | Griefing | − |
| spam | Спам | Spam | − |
| harassment | Преследование | Harassment | − |

Примеры:

```text
/like Fen0nim Помощь игрокам Спасибо за ресурсы
/dislike Fen0nim Грубость
/like Fen0nim friendly
/like Fen0nim "Helping players" Thank you
```

Названия сопоставляются без учёта регистра в выбранном языке. Поддерживаются фразы с пробелами и двойными кавычками. Самое длинное подходящее название в начале строки становится причиной, оставшаяся часть — комментарием; кавычки позволяют явно отделить причину. ID `friendly`, `rude` и другие остаются допустимыми. Положительная причина не подходит `/dislike`, отрицательная не подходит `/like`.

В `voting.yml`:

```yaml
reasons:
  friendly:
    enabled: true
    message: reason-friendly
    types: [POSITIVE]
  scam:
    enabled: false
```

В `lang/ru_RU.yml` и `lang/en_US.yml` соответственно:

```yaml
reason-friendly: 'Доброе общение'
```

```yaml
reason-friendly: 'Kindness'
```

Отсутствующие встроенные причины дополняются в памяти новыми значениями по умолчанию, без перезаписи файлов. Чтобы исключить причину, используйте `enabled: false`: она исчезнет из автодополнения/выбора и будет отклонена при новом голосовании, сохранив перевод в истории. Не удаляйте её перевод или ID ради выключения. Отсутствующий `enabled` означает `true`; должен оставаться хотя бы один включённый пункт. Пользовательские `message`, `types` и переводы сохраняются. Названия должны быть непустыми, уникальными в каждом языке, до 100 символов, без двойных кавычек и управляющих символов; конфликт с чужим ID отклоняется при запуске. Изменения причин и переводов требуют перезапуска плагина/сервера: `/repadmin reload` по-прежнему перечитывает только прежние правила доступа.

EN: reason labels and completion follow the viewer's selected language. Raw IDs remain accepted and stored. Configure `reasons.<id>.enabled` in `voting.yml`, and rename `reason-<id>` in each language file. Missing built-ins receive additive defaults; explicitly disable unwanted reasons. Restart after changing the catalog or translations. Disabled reasons remain localized in history; no historical IDs or votes are rewritten.

Внешний QA init script только для воспроизведения задавал forked test JVM логический temp-каталог с алиасом var→private/var. Оба параметра JSON/SQLITE упали: **2 failures**, исходная IOException `Symlink storage/backup ancestors are unsupported` в `AtomicFiles.safeAncestors:44`, далее `directories:31`, `JsonStorage:39` либо `SqlStorage.sqlite:43`, `StorageFixtures.local:29`, настоящий LocalStorageTest. Полные XML/стек и состояние алиаса сохранены вне репозитория. Это Linux-воспроизведение соответствующей ветки старого кода, не запуск Mac. После hotfix этот же сценарий и точный метод владельца повторены успешно с логическим JVM temp root; обходной temp override в обычной сборке не используется.

Обнаружены независимые общие дефекты:

1. Старый guard запрещал ссылки вплоть до корня FS, включая стандартные macOS /var, /tmp и /etc. Исключение возникает при общем открытии JSON/SQLite, поэтому множество feature tests не доходят до своих бизнес-проверок.
2. `syncDirectory` безусловно вызывал `FileChannel.force(true)` для каталога. В macOS JDK 25 этот вызов реализован через F_FULLFSYNC; fallback к fsync применяется только для нелокальных FS. Это не переносимый directory-fsync API и не устраняется выбором другого temp-каталога. Исходник OpenJDK jdk-25+36 macosx/native/libnio/ch/FileDispatcherImpl.c проверен и сохранён с URL/SHA. OS-отказ directory force моделируется в отдельной регрессии; нативный APFS вызов здесь не исполнялся.
3. File creation всегда требовал POSIX mode 0600; Windows provider требует ACL вместо POSIX attributes. Windows NIO также не открывает каталог как обычный FileChannel для directory sync.
4. Строгое холодное разрешение Gradle с неизменённой verification metadata 1.0.0 остановилось на 17 недостающих промежуточных POM/BOM/module checksums ещё при конфигурации plugin classpath. Тёплый кеш этого не обнаруживал.

Владелец подтвердил первичную ошибку на Mac в `LocalStorageTest.concurrentProfileCreationIsUniqueAndScoped`: JSON и SQLite падают с тем же сообщением и цепочкой AtomicFiles.safeAncestors:44 → directories:31 → JsonStorage:39/SqlStorage.sqlite:43 → StorageFixtures.local:29. Общий guard — подтверждённая причина исходных массовых ошибок. Остальные пункты — дополнительные найденные дефекты переносимости, а не утверждение о других причинах того исходного стека. Полный фактический per-user путь Mac не передавался; цепочка fixture: JVM java.io.tmpdir → JUnit @TempDir → json либо test.sqlite. При macOS логическом temp /var/folders/.../T каноническая ancestry проходит /private/var/folders/.../T. Известный /var alias не хардкодится в алгоритме. Простое `-Djava.io.tmpdir` для Gradle JVM также не гарантирует передачу свойства forked test JVM. Обычная 1.0.1 такого обходного пути не требует.

Linux release QA 1.0.0 использовала обычный Linux temp, поддерживаемый directory fsync и подготовленный кеш зависимостей; native Mac/Windows тогда не запускались. Исходный отчёт не переписан для сокрытия этого ограничения.

## Модель путей и сохранённая защита

`StoragePaths` проходит нормализованный абсолютный путь, канонизирует существующие компоненты, проверяет явную границу data folder и несуществующие листья повторно при создании. Явно заданный администратором data root фиксируется по logical/canonical path и fileKey. Его существующая ancestry доверена и канонизируется стандартным toRealPath без OS whitelist. JVM temp и process cwd также являются явно заданными runtime roots, их ancestry канонизируется до строгого обхода дочерних компонентов. Никаких специальных исключений для /var или иных OS путей в коде нет.

В Root.resolve разрешены внутренние symbolic links/junction при цели внутри того же canonical root. Ссылки с выходом наружу, traversal, абсолютный путь в относительной настройке и подмена root отвергаются. Несуществующие листья добавляются только ниже безопасного существующего предка. Low-level I/O получает канонический результат и по-прежнему отвергает неожиданные links/reparse: произвольный alias не является разрешением. Все четыре старых malicious-symlink теста сохранены; новая матрица проверяет inside/escape отдельно для JSON, SQLite, backup и lock. Изменение регистра и Windows 8.3 имени допускается только при сохранении того же родителя и file identity. Директории и owner-lock повторно проверяются по fileKey; замена или потеря блокировки приводит к отказу. Проверки до/после операции обнаруживают доступные смены родителей; полной race-safety против администратора ОС не обещается.

Внешний backup root явно выбирает администратор; его существующая ancestry канонизируется, а symlink самого root отвергается. Backup внутри data root разрешается относительно его границы, выход наружу запрещён.

Файлы создаются с POSIX 0600 либо единственным Windows ACL владельца каталога. Каталоги плагина и backups должны принадлежать учётной записи сервера; общие writable всем каталоги не являются доверенной границей. FS без POSIX/ACL отвергается. NOFOLLOW_LINKS сохранён, truncate выполняется после проверки родителя.

Все file force ошибки остаются ошибками. Replacement — только ATOMIC_MOVE в том же каталоге; copy/delete fallback нет. На Linux directory force выполняется и его ошибка не подавляется. На macOS Java 25 и Windows этот NIO backend не обещает directory fsync: сохраняются file force, атомарность замены, checksum и recovery, но **metadata durability при физическом отключении питания не подтверждена**. Резервные копии обязательны; это не эквивалент транзакционному SQL.

## Unix ownership: дополнительная воспроизведённая ошибка

Финальный аудит выявил реальный POSIX fcntl эффект: если текущий JVM уже держит lock, попытка второго StorageLease открывала второй FD, получала OverlappingFileLockException и закрывала этот FD. На Unix закрытие любого FD для inode может снять все process locks. Java FileLock.isValid оставался true, но отдельный JVM уже получал lock. Воспроизведение до исправления: LOCAL_DUPLICATE_REFUSED → CHILD_ACQUIRED /exit0 → ORIGINAL_JAVA_LOCK_REPORTS_VALID.

StorageLease теперь сериализует acquire/close через process registry и отвергает уже занятые canonical paths/file identities ДО открытия FD. Hard-link alias проверяется по fileKey. OS FileLock продолжает защищать между процессами; registry не заменяет его. Добавлены JSON/SQLite duplicate→second-JVM tests и hard-link→second-JVM regression. После исправления child получает отказ/exit42, первый владелец продолжает работу, close/restart освобождает блокировку. Нельзя доказать безопасность против произвольного стороннего кода того же JVM, открывающего/закрывающего lock-file в обход протокола; это вне доверенной модели cooperating owners.

Предыдущие 735 PASS/8 Paper launches сохранены как промежуточные evidence before-owner-fix; они не подменяют повторные финальные проверки изменённого JAR.

# Меню репутации, история и аудит

## Структура и размеры

Раньше административные экраны использовали один большой layout с повторяющейся строкой разделов. Теперь `/repadmin gui <игрок>` открывает **ровно 27 слотов**: голова и сводка игрока, по одной кнопке каждого раздела и действий. Раздел открывается отдельным экраном без повторной строки навигации по чужим функциям.

| Экран | Слоты |
| --- | --- |
| Главное административное меню | 27 |
| Доступ к голосованию, ручное изменение, перерасчёт | 18 |
| Подтверждение изменения | 18 |
| Доверие / Trust | 27 |
| Голоса, выданные оценки, pending, сигналы, связи, административная история, аудит, детали оценки | 18 / 27 / 36 / 45 по числу записей |
| Административная реабилитация | 18 / 27 / 36 / 45 / 54 с отдельным местом для действий |
| Технические подробности | 18 / 27 / 36 / 45, постранично |
| Публичный профиль `/rep gui <игрок>` | 45, симметричные группы |
| Выбор причины новой оценки | 18 / 27 / 36 / 45 |
| Публичные причины и история | 27 / 36 / 45 / 54, включая строку фильтров |
| Личная реабилитация | 18 / 27 / 36 / 45 / 54 по числу задач |
| Личные правила доступа | 27 |

Нижняя строка использует одинаковые позиции относительно конца inventory: предыдущая страница `size-9`, назад `size-7`, обновить `size-5`, закрыть `size-3`, следующая страница `size-1`. Неиспользуемые кнопки не рисуются. Back из подробностей возвращает исходную страницу и фильтр. У технических страниц отдельная пагинация.

Основной экран сохраняет полученные/выданные оценки, ожидающие проверки оценки, доверие, сигналы, связи, реабилитацию, административные изменения, аудит, перерасчёты, персональный доступ, изменение репутации и технические сведения. История доверия доступна внутри экрана доверия. Права разделов и действий прежние.

Ручное изменение предлагает зелёное `+1`, красное `−1` и установку `0`, показывает игрока и текущую репутацию. Произвольная величина по-прежнему задаётся `/repadmin set|add|remove <игрок> <число> <причина>`. Подтверждение показывает выбранное действие и затронутого игрока. Смена оценки, её аннулирование/восстановление, решения pending, классификация сигналов, перерасчёт, force и действия реабилитации требуют подтверждения.

Legacy-параметры layout/materials/slots в `administration.yml` и `gui.yml` продолжают валидироваться; существующие файлы не перезаписываются. Геометрия новых экранов определяется их назначением и числом записей, а не прежним общим `size: 54`; старые координаты разделов не навязывают повторные строки навигации. Размер страницы и лимиты выборок остаются настраиваемыми.

## Причины и история игрока

`/rep gui <игрок>` → история → все / положительные / отрицательные причины → конкретная причина → записи. Если включён `voting.yml: open-gui-on-profile`, тот же профиль открывается через `/rep <игрок>`. При прежнем текстовом режиме профиль содержит кликабельную подсказку истории, если доступны права GUI и истории.

У причины показаны **действующие оценки** и **все события журнала**. Можно переключать полный журнал и только действующие оценки. Запись показывает знак, переведённую причину, действие, дату, автора или получателя согласно направлению, комментарий и признак активности. Скрытая диагностика Trust/anti-abuse и административный аудит в публичную историю не передаются. Существующие права `use`, GUI и history проверяются при открытии, клике и завершении асинхронной загрузки.

Счётчики вычисляются из сохранённых записей текущего scope. JSON использует тот же авторитетный active index, что существующая история; SQLite/MySQL — `dr_active_votes`. Замены, отзывы и модерация не считаются действующими оценками, но остаются событиями журнала. Число событий не является суммой репутации или весов: например, добавление, замена и отзыв — три исторические записи и ноль действующих оценок. Механики истечения срока оценок в текущей модели нет; новое правило истечения не добавлялось.

Фильтры используют **канонические ID**, например `friendly`, `helpful`, `fair`, `rude`, `unfair`, а не русский/английский текст. Переключение языка не меняет запрос или сохранённую причину. Удалённая из конфигурации причина остаётся в группировке и истории: используется известный bundled-перевод либо «Архивная причина (ID)». Пустой ID в read-модели имеет отдельную локализованную категорию «Причина не указана» и точный фильтр; текущий валидируемый журнал требует непустую причину, а старые форматы до появления голосования не содержат записей голосов. Старые балансы не превращаются в вымышленные оценки; повреждённые записи не объявляются legacy-данными.

JSON вычисляет группировку сканированием ограниченного размером snapshot журнала на IO worker; для больших историй предпочтителен SQL. SQL-запросы параметризованы, страницы ограничены и выполняются на существующем IO executor. Новых схем, миграций или пересчёта репутации/Trust нет.

## Участники аудита

Для административных действий показываются **администратор: имя + UUID** и **игрок: имя + UUID**, тип действия, машинный ID действия, значение до/после, изменение, причина и дата. Другие типы записей сохраняют собственные роли: инициатор, автор оценки, получатель, связанный игрок. Это относится и ко второй/последующим страницам аудита.

Роли берутся из `actor`, `target`, `voter`, `neighbor` реальных записей. `vote`, `operation`, ID записи и предыдущей операции являются идентификаторами объектов, а не UUID игроков; имя игрока для них не угадывается. Проекция административной истории получает target из UUID владельца ledger. Исторические ledger/records не переписываются.

Имена берутся у онлайн-игрока либо из Paper profile/name cache по UUID (`completeFromCache(false, true)`), в том числе для offline-игроков. Нет синхронного Mojang-поиска по имени или fallback-чтения player NBT на main thread. Если записи нет в серверном кэше, показывается неизвестное имя; дисковый поиск по старым playerdata не запускается. Для неизвестного имени используется локализованная подпись, UUID сохраняется. Console/System подписываются явно и не получают фиктивного UUID игрока. Служебный нулевой UUID отсутствующей цели показывается как «—», а не как неизвестный игрок. В технических подробностях поля участников имеют отдельные подписи имени и UUID; неизвестное техническое поле имеет локализованный заголовок с исходным машинным ключом.

## Начальный допуск и уведомления

`/repadmin force <игрок> [on|off|status]`, право `dexturreputation.admin.force` (default: op). Без режима / `on` включают постоянный UUID/scope bypass только `minimum-playtime-seconds` и `minimum-account-age-seconds` (время после первого входа **на этот сервер**). `off` возвращает требования, `status` только читает. Повторный установленный режим не создаёт лишнего изменения.

Не обходятся права, известность получателя, self-vote, причины/комментарии, дневной лимит, общий/парный cooldown, повторные оценки, личная блокировка, серверные политики и anti-abuse. Реальные Paper-факты не подменяются; Trust, вес и pending продолжают использовать их. Состояние и аудит хранятся прежним способом под внутренним ключом `reputation.initial-eligibility`; отдельная миграция не нужна.

Инициатор получает короткое локализованное подтверждение; затронутые онлайн-игроки — соответствующее уведомление. Это распространяется на оценки/отзыв, ручные изменения, ограничения, force, модерацию и администрирование восстановления. При модерации уведомляется также онлайн-автор оценки. Повторные события и совпадающие роли дедуплицируются в памяти. Существующий `notify-target` сохраняется. Offline inbox не добавлен; отдельные уведомления о смене уровня сохранены.

## Локализация и жизненный цикл

Оба bundled-каталога `ru_RU` и `en_US` содержат одинаковые ключи. Новые ключи добавляются fallback-механизмом в памяти без перезаписи пользовательских файлов; намеренно настроенный собственный текст администратора сохраняется. Введённые пользователями комментарии и свободные причины аудита остаются исходными данными и не переводятся автоматически. Используются существующие `default-language` и `/rep language ru_RU|en_US`, MiniMessage и literal-подстановки. Заголовки голубые, действия/навигация жёлтые, положительные/отрицательные операции зелёные/красные, UUID подписаны вторичным серым текстом.

Inventory-операции выполняются на Paper main thread; переходы из InventoryClickEvent отложены на следующий тик. Перемещение предметов, shift/number/offhand/drag отменяются. Права проверяются повторно, подтверждения одноразовые, имеют срок и fingerprint; быстрые повторные клики не дублируют изменение. Закрытие/выход/disable отменяют неподтверждённые действия. `/repadmin reload` перечитывает прежние правила доступа и закрывает открытые меню, чтобы старые кнопки не переживали смену правил; полноценный Bukkit `/reload` не добавлен.

## Локализованные причины и игроковое меню

`/rep gui [игрок]` использует пять рядов без декоративного заполнителя. Нумерация слотов ниже начинается с нуля:

| Ряд | Слоты | Назначение |
|---|---|---|
| 1 | 2 / 4 / 6 | Репутация / профиль игрока / уровень и прогресс |
| 2 | 11 / 13 / 15 | История событий / полученные причины / мои отправленные голоса |
| 3 | 20 / 22 / 24 | Положительный голос / отзыв / отрицательный голос |
| 4 | 29 / 31 / 33 | Моё восстановление / помощь / мои возможности |
| 5 | 38 / 40 / 42 | Назад / обновить / закрыть |

При просмотре себя действия голосования скрыты. Кнопки восстановления, отправленных голосов и возможностей относятся к зрителю и явно подписаны «Моё/Мои». Остальные разделы описывают выбранного игрока. Скрытые настройками или правами функции не получают активной кнопки. Сводки содержат актуальные значения, действия — описание и подсказку ЛКМ.

Заголовки, имена предметов, lore и подсказки всех пяти GUI задают `italic=false`, чтобы убрать стандартный курсив Minecraft. Явно настроенный администратором `<italic>` остаётся намеренным оформлением. Админское меню сохраняет прежнюю структуру. Кнопка «Обновить» перечитывает профиль, историю, восстановление и личные возможности; существующее обновление админских разделов сохранено. История сохраняет направление, фильтр причины и страницу. Обновление восстановления не запускает программу и не меняет прогресс само по себе; оно читает состояние обычным сервисом.

Названия причин берутся из языка зрителя, включая выключенные причины в истории. Неизвестная удалённая причина показывается как «Архивная причина» без внутреннего ID. Конфигурация, полный каталог и примеры ввода — [VOTING.md](VOTING.md#локализация-и-настройка-причин).

Один целевой runtime-прогон: `scripts/admin-ux-smoke.py --ux-polish` с обычными аргументами `--accept-eula --directory <новый-каталог> --paper-jar <Paper.jar> --mojang-cache <mojang.jar>`. Режим проверяет сетевые сообщения, RU-команды, RU/EN причины, координаты симметричных групп, реальные Adventure-компоненты и обновление разделов. Ручной осмотр графического Minecraft-клиента этим не заменяется.

Проверка текущего UX-прохода: `./gradlew clean build --no-build-cache` — успешно, **591 тест**, 0 ошибок и пропусков (domain 10, application 95, Paper 138, storage 348; добавлено 12 точечных проверок). Отдельный `runtimeProbeJar` собран успешно. Целевой Paper 26.2 build 134 / Java 25 прогон с JSON подтвердил RU `/like` и `/dislike`, стабильные ID и комментарии, RU/EN историю, симметричные слоты, отсутствие наследуемого курсива, обновление профиля/истории/восстановления/доступа/админских экранов и реальные пакеты уведомлений автора и цели. После исправления распознавания QA-маркера в клиенте повторный короткий прогон завершился полностью успешно. Ручной графический осмотр и отдельная Docker SQL-матрица в этом узком проходе не выполнялись.

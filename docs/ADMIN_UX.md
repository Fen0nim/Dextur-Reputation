# Управление игроком и уведомления

`/repadmin gui <игрок>` открывает краткий обзор: имя, репутация со знаком, уровень, доступ к голосованию, начальный допуск без ожидания, Trust, сигналы и восстановление. Закрытые административные данные доступны только с соответствующими правами.

## Меню

- Верхние значки переключают обзор, полученные оценки, pending, Trust, сигналы, связи, восстановление, административную историю, аудит и проверку данных.
- В обзоре есть отдельные кнопки выданных оценок, изменения репутации и доступа к голосованию.
- Изменение репутации предлагает +1, −1 и установку 0. Для произвольного числа используйте `set/add/remove` с причиной в команде. Такие изменения остаются административным вкладом, не переписывают историю голосов.
- В доступе отдельно показаны личная блокировка, настроенное серверное правило, итог правила с персональными ограничениями и начальный bypass. Снятие личной блокировки не отменяет серверное правило.
- История показывает автора/получателя, понятную причину и состояние. ЛКМ открывает оценку; изменение и восстановление требуют подтверждения. В pending ЛКМ одобряет, ПКМ отклоняет — оба клика сначала открывают подтверждение.
- Сигналы предлагают явно подписанную классификацию; результат показывается перед подтверждением. Классификация сама по себе не назначает скрытый штраф Trust.
- Доступные действия восстановления зависят от состояния программы. Пауза, продолжение, отмена и сброс этапа проверяют `dexturreputation.recovery.admin` и требуют подтверждения.
- Информационные предметы так и подписаны. Каждая кнопка имеет описание и подсказку. Назад, закрыть, обновить и пагинация работают одинаково в разделах.
- UUID, технические поля и длинные сведения вынесены в отдельный постраничный просмотр. Они не заменяют имя или описание действия на основных экранах.

Изменения проверяют права до открытия и перед исполнением. Подтверждение одноразовое, ограничено временем и отклоняется при изменившемся просмотре. Закрытие меню отменяет ещё не подтверждённое действие; уже подтверждённая принятая операция завершается обычным образом.

## Начальный допуск к голосованию

```text
/repadmin force <игрок>
/repadmin force <игрок> on
/repadmin force <игрок> off
/repadmin force <игрок> status
```

Право: `dexturreputation.admin.force`, по умолчанию только операторам. Команды принимают известное имя или полный UUID, не выполняют внешнего поиска и не создают вымышленную личность. Состояние привязано к UUID и текущему scope.

Без режима и с `on` включается обход только `minimum-playtime-seconds` и `minimum-account-age-seconds`: возраст означает время после первого входа на этот сервер. `off` восстанавливает настроенные требования, `status` только читает состояние. Повторный `on/off` с уже установленным состоянием не создаёт лишнего изменения или уведомления цели.

Остаются проверки прав, известного получателя, self-vote, причин/комментариев, дневного лимита, общего и парного cooldown, повторных оценок, личной блокировки, серверных политик и anti-abuse. Реальные playtime/first-join facts не подменяются: Trust, вес, pending и защита от манипуляций продолжают использовать их.

Bypass хранится в существующем административном override-ledger под зарезервированным ключом `reputation.initial-eligibility`. Это внутренний ключ данных, не сообщение игроку и не общий `FORCE_ALLOW` для политики голосования. `/repadmin policy` не позволяет менять этот ключ: нужен отдельный `force` и его право. Существующие JSON/SQLite/MySQL сохраняют состояние и аудит через текущий механизм; новой SQL-схемы или формата JSON нет. Состояние переносится стандартной миграцией и сохраняется после рестарта. В аудите видны включение/отключение, администратор и причина.

## Обратная связь

| Действие | Инициатор | Затронутый онлайн-игрок |
| --- | --- | --- |
| Лайк, дизлайк, отзыв | Краткое подтверждение с переведённой причиной | Автор, действие и причина |
| Pending | Сообщение об ожидании, без ложного изменения репутации | Сообщение об ожидающей оценке |
| Одобрение/отклонение, аннулирование/восстановление | Администратор получает результат | Получатель и онлайн-автор оценки получают понятный новый статус |
| Set/add/remove | Изменение и итог | Администратор, причина и итог |
| Блокировка/разблокировка | Подтверждение | Ограничение или восстановление доступа |
| Force ON/OFF | Результат или текущее состояние | Новые начальные условия голосования |
| Проверка/согласование данных | Результат проверки | Нейтральное уведомление без скрытых Trust/anti-abuse данных |
| Администрирование восстановления | Понятное название действия и игрок | Состояние программы; низкоуровневые события одной операции объединены |

Самостоятельное действие не создаёт второго сообщения той же роли. Дубликаты post-commit событий ограниченно дедуплицируются в памяти; потерянные сообщения не обещают долговечной доставки. Offline-цель не мешает операции: inbox и доставка после входа не добавлены. Отдельное уведомление о реальном изменении уровня сохраняется как отдельное событие.

Для оценок сохраняется настройка `voting.yml: notify-target`; при её явном отключении уведомления получателя/автора о статусе подавляются. Все сообщения используют язык конкретного получателя и literal Adventure-подстановки.

## Настройки и проверка

Новые тексты находятся в `lang/ru_RU.yml` и `lang/en_US.yml` (`admin7-ui-*`, `admin-force-*`, `admin-success-*`, `admin-target-*`, `vote-success-*`, `vote-target-*`, `vote-reviewed-*`). Недостающие ключи подставляются из bundled-каталога в памяти. Файлы администратора не перезаписываются; новый GUI использует существующие размеры/слоты `administration.yml`. Маленькие допустимые области контента получают дополнительные страницы.

Справка разделена на `/repadmin help 1`, `2`, `3`. Администрирование восстановления также доступно как `/repadmin recovery <игрок> <действие> [причина]`; прежний `/rep admin recovery` сохранён.

Focused QA: `scripts/admin-ux-smoke.py` запускает Paper 26.2 / Java 25, три настоящих protocol-клиента, клики inventory, проверку локализованных lore и сетевых сообщений, затем рестарт. Использует новый изолированный каталог и явное принятие EULA. Только QA-настройки сокращают cooldown и порог демонстрации pending; начальные playtime/age требования сохраняются. Это проверка реального сервера, а не ручной визуальный осмотр стандартным графическим клиентом.

Финальная проверка этого изменения: `./gradlew clean build --no-build-cache` — 553 теста (domain 10, application 95, Paper 107, storage 341), без ошибок и пропусков. Отдельно прошли два focused-контракта force с MariaDB и MySQL. Финальный JAR проверен на Paper 26.2-134 / Java 25: JSON и SQLite, по два запуска, включая рестарт; подтверждены маршруты GUI, правильный получатель подтверждения, отмена изменений, ограничения при force, pending и уведомления автора/получателя реальными chat-пакетами. Проверка упаковки подтвердила неизменность 41 класса публичного API и отсутствие QA-классов/данных сервера в production JAR. Ручной визуальный осмотр графическим клиентом не выполнялся.
